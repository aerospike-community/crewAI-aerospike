## 개요

Aerospike 백엔드는 CrewAI의 통합 `Memory`가 영속화에 사용하는 `StorageBackend` 프로토콜의 구현입니다. 이 백엔드는 `crewai.memory.storage.aerospike_storage`에 있으며, 선택적 extra인 `pip install "crewai[aerospike]"` 뒤에 제공되어 `aerospike-sdk` 클라이언트를 설치합니다. 클라이언트는 필요할 때만 import되므로 사용하지 않는 프로젝트에는 아무 변화도 없습니다.

논리적 스코프 하나는 Aerospike 레코드 하나로 저장되고, 레코드의 bin에 해당 스코프의 메모리들이 담깁니다. 각 메모리의 임베딩은 그 레코드 안에 네이티브 벡터 값으로 저장됩니다. 검색은 근사 최근접 이웃 조회가 아니라 브루트포스(brute-force) 스캔 후 순위 매기기입니다. 아래 절에서 각 결정과 그 비용을 설명합니다. 먼저 백엔드를 써 보려면 [빠른 시작](/edge/ko/learn/aerospike-memory-quickstart)을 따라 하세요.

## 연결 방식

스토리지 스펙으로 백엔드를 선택하고, 시작 시 팩토리를 한 번 등록합니다.

```python
from crewai import Memory
from crewai.memory.storage.aerospike_storage import aerospike_storage_factory
from crewai.memory.storage.factory import set_memory_storage_factory

set_memory_storage_factory(aerospike_storage_factory)
memory = Memory(storage="aerospike://127.0.0.1:3000/test")
```

스펙은 `aerospike://host:port/namespace` 형식이며, 백엔드가 사용하는 set의 이름을 정하는 선택적 쿼리 매개변수 `set_prefix`가 하나 있습니다(기본값 `crewai_memory`). `aerospike_storage_factory`는 `aerospike://`로 시작하는 스펙에는 스토리지를 반환하고 그 밖의 모든 스펙에는 `None`을 반환하므로, 다른 스펙에서는 내장 LanceDB와 Qdrant Edge 선택이 그대로 동작합니다. `aerospike://`로 시작하지만 형식이 잘못된 스펙은 `ValueError`를 발생시키며, 다른 백엔드로 넘어가지 않습니다.

스펙 문법은 엄격한 허용 목록입니다.

| 부분 | 규칙 |
|---|---|
| 길이와 문자 | 최대 512자, 공백이나 제어 문자 없음, `%` 없음, 프래그먼트 없음, `@` 없음(자격 증명은 지원되지 않음) |
| 호스트 | DNS 이름, IPv4 주소 또는 대괄호로 감싼 IPv6 주소 |
| 포트 | 필수, 1에서 65535 |
| 네임스페이스 | 정확히 하나의 경로 세그먼트, 영문자, 숫자, 밑줄 또는 하이픈 1~31자 |
| `set_prefix` | 선택, 한 번만, 영문자, 숫자 또는 밑줄 1~40자 |
| 그 밖의 모든 것 | `ValueError`로 거부됩니다. 오류 메시지는 스펙의 값을 반복하지 않습니다 |

모든 설정은 스펙에서 가져옵니다. 라이브러리는 환경 변수를 읽지 않습니다. 프로세스 안에서 호스트와 포트마다 클라이언트 연결이 하나씩 만들어져, 이를 사용하는 모든 스토리지가 공유합니다. 따라서 스토리지를 닫아도(`Memory.close()`가 하는 일입니다) 연결은 열린 채로 남고, 인터프리터가 종료될 때 연결이 닫힙니다.

## 데이터 모델

스토어는 set 접두사 `P`에서 이름을 딴 두 개의 set을 사용합니다. `P`에는 스코프 레코드가, `P_meta`에는 스토어 수준 정보를 담은 레코드 하나가 있습니다.

### 스코프 레코드

각 스코프 레코드의 키는 문자열 `<scope>|<chunk>`이며, 예를 들어 `/team/sales|0`입니다. 스코프는 맨 앞에 슬래시를 붙이고 끝의 슬래시는 없애 정규화하며, 루트 스코프는 `/`입니다. 청크 번호는 0에서 시작합니다(아래 청킹 참고).

| Bin | 타입 | 내용 |
|---|---|---|
| `scope` | 문자열 | 정규화된 스코프 경로 |
| `chunk` | 정수 | 청크 번호 |
| `anc` | 문자열 리스트 | 스코프와 모든 상위 스코프, 예: `["/", "/team", "/team/sales"]` |
| `cats` | 문자열 리스트 | 이 레코드에 지금까지 추가된 고유 카테고리 |
| `created_at` | 정수 리스트 | 레코드에 있는 각 메모리의 생성 시각, UTC 기준 epoch 이후 마이크로초 |
| `mem` | 문자열에서 맵으로의 맵 | 메모리 id에서 메모리 항목으로 |
| `emb` | 문자열에서 벡터로의 맵 | 메모리 id에서 메모리의 임베딩으로, 네이티브 float32 벡터 값 |
| `bytes` | 정수 | 청킹에 사용하는, 누적 페이로드 크기 추정치 |

`mem`의 각 항목은 다음 키를 가진 맵입니다.

| 키 | 타입 | 내용 |
|---|---|---|
| `c` | 문자열 | 메모리 내용 |
| `cat` | 문자열 리스트 | 메모리의 카테고리 |
| `md` | 문자열 | JSON 텍스트로 된 메타데이터 |
| `imp` | 실수 | 중요도 |
| `ts` | 정수 | 생성 시각, UTC 기준 epoch 이후 마이크로초 |
| `la` | 정수 | 마지막 접근 시각, UTC 기준 epoch 이후 마이크로초 |
| `src` | 문자열 | 출처, 없으면 생략 |
| `prv` | 불리언 | 메모리가 비공개인지 여부 |

### 메타 레코드

`P_meta` set에는 키가 `store`인 레코드 하나가 있습니다. `dim` bin은 스토어의 임베딩 차원으로 첫 임베딩이 저장될 때 설정되고, `fmt` bin은 저장 형식 버전으로 현재 1입니다.

### 이러한 선택의 이유

스코프당 레코드 하나와 맵 및 리스트 bin은 메모리가 쓰이는 방식에 잘 맞습니다. 나열, 개수 세기, 설명, 삭제는 스코프 하나 또는 스코프 하위 트리 단위로 이루어지므로 한 스코프의 메모리를 함께 읽고, 스코프에 대한 쓰기는 레코드 하나에 대한 원자적 호출 한 번입니다. 메모리당 레코드 하나로 하면 메모리마다 인덱스 항목과 키가 필요하고, 이 모든 작업이 작은 읽기 여러 번으로 바뀝니다. 대가는 레코드가 커질 수 있다는 점이며, 그래서 레코드를 청크로 나눕니다.

임베딩은 자체 bin에 두어 읽기 종류마다 필요한 것만 건드리게 합니다. 나열, 스코프 정보, 카테고리 개수는 `mem`만 읽습니다. 검색 순위 계산은 `emb`만 읽고, 그다음 결과 항목을 키로 가져옵니다. 임베딩은 패킹된 바이트가 아니라 메모리 id를 키로 하는 맵 안의 네이티브 벡터 값이므로, 저장된 데이터가 벡터로 타입이 지정되고 코드에 바이트 순서나 패킹 규칙이 필요하지 않습니다.

메타데이터는 임의의 딕셔너리이므로 JSON 텍스트로 저장합니다. 텍스트는 어떤 구조든 정확히 왕복합니다. 메타데이터 필터는 디코딩된 값에 대해 클라이언트가 적용하며, 메타데이터에는 인덱스가 없습니다.

타임스탬프는 UTC 기준 epoch 이후 마이크로초 단위의 정수입니다. 전달하는 naive datetime은 UTC로 취급하고, 시간대 정보가 있는 datetime은 UTC로 변환하며, 읽을 때는 naive UTC datetime을 반환합니다.

스코프 접두사는 경로 세그먼트를 인식합니다. 접두사 `/a`는 `/a`와 `/a/b`에 일치하고 `/ab`에는 일치하지 않습니다.

## 청킹

스코프는 보통 레코드 하나, `<scope>|0`에 저장됩니다. 레코드는 통째로 쓰고 읽으며 서버가 크기를 제한하므로(보통 1 MiB, 네임스페이스별로 설정), 계속 커지는 스코프는 여러 레코드로 나뉩니다. 백엔드는 `bytes` bin에 페이로드 추정치를 보관합니다. 추정치에는 메모리마다 내용, 메타데이터 텍스트, 카테고리, 출처와 항목당 고정 오버헤드가 포함되고, 임베딩 차원당 4바이트와 임베딩의 작은 오버헤드가 더해집니다.

청크 한도는 기본 262,144바이트이며 `AerospikeStorage`의 `chunk_limit_bytes` 인자로 최대 524,288바이트까지 설정할 수 있습니다. 저장으로 레코드가 한도를 넘게 되면 백엔드는 들어가지 않는 메모리를 다음 청크 레코드인 `<scope>|1` 등에 넣으므로, 어떤 청크도 한도를 넘겨 채워지지 않습니다. 한도보다 큰 메모리 하나는 자기만의 청크를 갖습니다. 추정치가 낮게 나와 서버가 레코드가 너무 크다고 응답하면 쓰기는 한 번 다음 청크로 이동합니다. 항목은 기록된 청크에 그대로 남으며, 메모리의 스코프를 바꾸는 update만 항목을 옮깁니다.

## 인덱스

백엔드는 프로세스에서 set 접두사에 처음 연결할 때 보조 인덱스 네 개를 만듭니다. 이미 있는 인덱스를 만들어도 오류가 아니므로, 다시 연결하거나 다른 프로세스가 먼저 시작해도 문제가 없습니다.

| 인덱스 | Bin | 용도 |
|---|---|---|
| `P_scope_idx` | `anc`, 문자열 리스트 | 검색, 나열, 개수 세기, 삭제를 스코프 하위 트리로 좁힘 |
| `P_cats_idx` | `cats`, 문자열 리스트 | 카테고리로 좁힘 |
| `P_created_idx` | `created_at`, 정수 리스트 | 특정 시각보다 오래된 메모리 삭제 |
| `P_memids_idx` | `mem`, 문자열 맵 키 | id로 메모리 찾기 |

메모리 id 인덱스가 있는 이유는 id로 가져오기, 업데이트, touch, 삭제에는 스코프가 없어서, 인덱스가 없으면 백엔드가 전체를 스캔해야 하기 때문입니다. 인덱스는 후보 레코드만 좁힙니다. 백엔드는 항상 항목에 대해 정확한 필터를 다시 확인하므로, 과대 근사하는 bin(늘어나기만 하는 `cats`와 `anc`)은 읽기를 조금 더 쓸 뿐 잘못된 결과를 만들지 않습니다.

## 검색과 비용 모델

검색은 브루트포스(brute-force) 스캔 후 순위 매기기입니다. 근사 최근접 이웃 인덱스는 없습니다. 쿼리는 서버에서 후보 스코프 레코드를 좁히는데, 스코프 접두사에는 스코프 인덱스를, 카테고리가 주어지면 카테고리 인덱스를 사용합니다. 그다음 모든 후보 메모리의 임베딩을 읽고 클라이언트에서 numpy로 코사인 유사도를 계산합니다. 전송되는 바이트와 계산량은 후보 메모리 수에 임베딩 차원을 곱한 값에 비례해 선형으로 늘어납니다.

계산 예시: 1,536차원의 후보 메모리 10,000개는 10,000 곱하기 1,536 곱하기 4바이트, 즉 스코프 없는 쿼리 한 번에 읽는 임베딩이 약 61 MB입니다. 3,072차원에서는 같은 쿼리가 약 123 MB를 읽습니다.

주된 제어 수단은 쿼리의 스코프입니다. 스코프 접두사가 있는 쿼리는 그 접두사 아래의 레코드만 읽으므로, 답이 어디에 있는지 알면 항상 `recall`에 스코프를 전달하세요. 카테고리는 후보를 더 좁힙니다.

각 메모리의 벡터가 스코프 레코드의 맵 안에 중첩되어 있고 레코드 하나에 많은 메모리가 들어 있으므로 순위 계산은 클라이언트에서 실행되며, 서버 측 벡터 순위 계산은 사용하지 않습니다. 점수를 매긴 뒤 백엔드는 가장 좋은 결과의 항목만 키로 가져와 정확한 카테고리 및 메타데이터 필터를 적용합니다.

검색 결과에는 다음 특성이 있습니다.

- 점수는 -1에서 1 사이의 코사인 유사도이며, 길이가 0인 벡터는 0.0점입니다.
- `min_score`는 경계값을 포함하며, 결과는 점수순, 그다음 id순으로 정렬됩니다.
- 임베딩 없이 저장된 메모리는 나열하고 가져올 수 있지만 순위에는 오르지 않습니다.
- 검색은 메모리를 최대 50,000개, 스코프 레코드를 최대 100,000개 읽습니다. 그 한도를 넘으면 경고를 기록하고 읽은 것만으로 순위를 매기므로, 매우 큰 스토어에 대한 매우 넓은 쿼리는 불완전한 결과를 돌려줄 수 있습니다. 쿼리의 스코프를 좁히면 이를 피할 수 있습니다.

## 임베딩 차원

스토어는 처음 저장한 임베딩의 차원을 메타 레코드에 생성 전용(create-only) 방식으로 기록하므로, 동시에 시작한 두 프로세스가 같은 값에 합의합니다. 이후 길이가 다른 임베딩을 저장하거나 길이가 다른 쿼리로 검색하면 `EmbeddingDimensionMismatchError`(`crewai.memory.storage.backend`)가 발생합니다.

보통 임베더가 바뀌었다는 뜻이며, 예를 들어 1,536차원 모델에서 3,072차원 모델로 바뀐 경우입니다. 복구하려면 스토어를 만든 임베더를 설정하거나, `memory.reset_all()`로 스토어를 비우고 다시 저장하세요. 전체 초기화는 이 set 접두사의 두 set만 truncate하고 저장된 차원을 지우므로, 다음 임베딩이 새 차원을 정합니다. 다른 set은 건드리지 않습니다.

## 일관성과 동시성

스코프 레코드 하나에 대한 각 쓰기는 맵 upsert, 리스트 append, 크기 갱신을 합친 원자적 호출 한 번이므로, 같은 스코프에 대한 동시 저장이 서로를 덮어쓰지 않습니다. 여러 스코프에 걸친 저장은 여러 레코드를 쓰며, 이 쓰기들은 묶음으로는 원자적이지 않습니다. 메모리를 다른 스코프로 옮기는 update는 새 레코드를 쓴 뒤 이전 레코드를 제거하므로, 읽는 쪽에서 잠깐 두 곳 모두에서 메모리가 보일 수 있습니다.

제거는 레코드를 읽고 세대(generation) 확인과 함께 다시 쓰며, 다른 쓰기가 먼저 끼어들었다면 최신 레코드로 재시도합니다. 다섯 번 시도한 뒤에는 `RuntimeError`를 발생시킵니다. 메모리가 하나도 남지 않은 레코드는 삭제됩니다.

프로세스당 클라이언트 하나가 공유됩니다. 비동기 메서드 `asave`, `asearch`, `adelete`는 동기 구현을 워커 스레드에서 실행하므로 이벤트 루프를 막지 않으며, 같은 공유 클라이언트를 사용합니다.

## 기본 제공 백엔드와의 차이

Aerospike 백엔드는 기본 제공 LanceDB 및 Qdrant Edge 백엔드와 같은 `StorageBackend` 프로토콜을 따르지만, 몇 가지 동작이 다릅니다. 기존 프로젝트를 전환하기 전에 확인하세요.

| 동작 | Aerospike | Qdrant Edge | LanceDB |
|---|---|---|---|
| 스코프 접두사 `/a` | 경로 세그먼트 기준으로 일치: `/a`와 `/a/b`는 일치하고 `/ab`는 일치하지 않음 | Aerospike와 같이 경로 세그먼트 기준으로 일치 | 일반 문자열 접두사로 일치: `/ab`도 일치 |
| 점수 | 코사인 유사도, -1에서 1 | 코사인 유사도, -1에서 1 | `1/(1+distance)`, 항상 0보다 큼 |
| 기본 `min_score` 0.0 | 유사도가 음수인 결과를 제외 | 유사도가 음수인 결과를 제외 | 음수 점수가 없으므로 아무것도 제외하지 않음 |
| `delete(record_ids=[])` | ID 필터가 없는 것처럼 동작 | ID 필터가 없는 것처럼 동작 | ID 필터가 없는 것처럼 동작 |

점수가 서로 다른 공식에서 나오므로 같은 `min_score` 임계값이 백엔드마다 같은 결과를 고르지 않습니다. 전환한 뒤에는 다시 조정하세요. 세 백엔드 모두 빈 `record_ids` 목록을 ID 필터가 없는 것처럼 처리합니다. 다른 필터가 없으면 `delete(record_ids=[])`는 모든 메모리를 삭제하고, 다른 필터가 있으면 해당 필터가 삭제 대상을 결정합니다. 특정 ID만 삭제하려면 ID 목록을 먼저 만들고 비어 있지 않은지 확인하세요.

인증은 아래 제한 사항에서 설명하듯이 이번 릴리스의 범위에 포함되지 않습니다.

## 제한 사항

| 제한 | 값 |
|---|---|
| 호출당 결과 수(`limit`) | 양의 정수, 1,000으로 제한 |
| 검색 또는 나열 한 번이 읽는 메모리 | 50,000개, 이후 경고와 잘라냄 |
| 검색 또는 나열 한 번이 읽는 스코프 레코드 | 100,000개, 이후 경고와 잘라냄 |
| 호출당 레코드 id | 최대 10,000개, 초과 시 `ValueError` |
| 서버에서 좁히는 카테고리 | 최대 32개. 그 이상은 필터가 클라이언트에서 계속 적용됨 |
| 스코프 | 최대 512자, 32세그먼트 |
| 카테고리 또는 메모리 id | 최대 1,024바이트 |
| 메모리 하나 | 추정 페이로드 최대 524,288바이트 |
| 청크 한도 | 기본 262,144바이트, 최대 524,288 |

저장 시 크기 제한을 넘으면 아무것도 쓰기 전에 `ValueError`가 발생합니다. 빈 `record_ids` 리스트는 아무것도 삭제하지 않습니다.

만료는 없습니다. 백엔드는 TTL(time to live)을 설정하지 않으므로 메모리는 삭제할 때까지 남습니다.

이 릴리스에는 인증이 없습니다. 스토리지 스펙은 자격 증명을 받지 않으며 백엔드는 자격 증명 없이 연결합니다. Aerospike 서버는 사설 네트워크에서 실행하거나 개발 시에는 루프백 주소에 바인딩하고, 신뢰할 수 없는 네트워크에 노출하지 마세요. 네임스페이스에 접근할 수 있는 누구나 그 레코드를 읽고 바꿀 수 있습니다.

set 접두사 하나가 신뢰 경계 하나입니다. 스코프와 `private` 플래그는 recall 시 메모리를 정리하고 거르는 용도이지 접근 제어가 아닙니다. set 접두사 아래에 저장된 모든 것은 그곳에 접근할 수 있는 모든 클라이언트에게 보이므로, 분리해야 하는 데이터에는 별도의 네임스페이스나 서버를 사용하세요.

### 클라이언트 요구 사항

임베딩은 네이티브 벡터 값으로 저장되므로, 백엔드에는 맵 안을 포함해 벡터 값 타입을 지원하는 `aerospike-sdk` 클라이언트가 필요합니다. 현재 릴리스된 `aerospike-sdk`가 이를 지원하는지는 확인되지 않았습니다. 이 백엔드에 의존하기 전에 사용하는 클라이언트가 벡터 타입을 제공하는지 확인하고, 백엔드가 그 지원에 의존한다고 간주하세요.
